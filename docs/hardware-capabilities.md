# PS5 DualSense 硬件能力、驱动边界与高清触感技术方案

本文档系统梳理 **PS5 DualSense (DS5)** 控制器的全部硬件能力、在本项目中的支持度边界、信号源还原度差距，以及未来跨平台（Linux & Windows）实现 **高清触感（Voice-Coil 音频触感）** 的架构方案。

> **核心结论**：
> 外部驱动框架的上限**不在 HID 协议，而在「信号从哪来」**。
> Astro's Playroom 等第一方大作之所以体验震撼，是因为它具备游戏引擎内部预先编排好的“触感音频谱（Haptic Audio Tracks）”；外部适配框架无法直接获取游戏内主观感知资产，只能基于物理遥测反推或按键行程驱动。
> 凡是基于 HID 协议能控制的物理量（扳机阻力、电机振幅、灯光、按键与传感器），本项目已基本吃满；真正的物理鸿沟在于 **USB 音频通道驱动的高清音圈触感**。

## 一、DS5 硬件能力 × 本项目支持度全景表（14 项）

DualSense 硬件通道在接入 PC 后被拆分为两个独立设备：**HID 游戏控制器** 与 **UAC2 4 声道 USB 声卡**。

| # | 硬件能力 | 通道类型 | 支持状态 | 说明 / 代价 |
|---|---|---|---|---|
| 1 | **自适应阻力扳机 L2/R2** | HID 输出 | ✅ 100% | 语义封装 8 种效果（feedback / weapon / vibration / slope×2 / machine / rigid / section）+ `p0..p9` 裸参数 → 协议里任何 mode 都能打。 |
| 2 | **双马达传统震动 L/R** | HID 输出 | ✅ 100% | `0..255` 幅度控制，支持内置正弦波（sine）与方波（square）动态调幅，用于 ABS 脉冲与后坐力。 |
| 3 | **灯条 RGB (Lightbar)** | HID 输出 | ✅ 100% | 规则里 `target: lightbar`，支持 24-bit 独立 RGB 驱动，内置空闲/就绪/低电量报警/充电呼吸灯。 |
| 4 | **玩家指示灯（5 颗 LED）** | HID 输出 | ✅ 100% | 字段已就位，`valid_flag2` 只有在值非 0 时才置位 `0x04`，避免把系统默认的玩家分配指示关掉。 |
| 5 | **静音键指示灯 (Mute LED)** | HID 输出 | ✅ 100% | 规则引擎直接暴露 `target: mute_led`，表达式值 `≥ 0.5` 触发橙色指示灯亮起。 |
| 6 | **模拟扳机行程（输入）** | HID 输入 | ✅ 100% | `0..255` 模拟量，归一化 `[0, 1]`，FPS 瞄准挡墙与射击断点全靠它。 |
| 7 | **物理按键 / 双摇杆（输入）** | HID 输入 | ✅ 100% | 18 个按键 + 十字键 (D-pad) + 双摇杆（含 L1/R1/PS/触控板下压/静音键），摇杆坐标 `[-1, 1]`。 |
| 8 | **陀螺仪 / 加速度计（输入）** | HID 输入 | ✅ 100% | 解析输入报告 `p[15..26]`，3 轴角速度 (`gyro_x/y/z`) 与 3 轴线性加速度 (`accel_x/y/z`)，小端 int16 归一化至 `[-1, 1]`。 |
| 9 | **触控板坐标（输入）** | HID 输入 | ✅ 100% | 提取首个有效触点的 12 位压缩坐标 (`touch_x`, `touch_y`)，归一化映射至 `[0, 1]`，附带 `touch_active` 状态。 |
| 10 | **电量 / 充电状态（输入）** | HID 输入 | ✅ 100% | 解析输入报告 `p[52]`，电量以 10% 步进归一化至 `0.0..1.0`（`battery`），高半字节提取充电标志位（`charging`）。 |
| 11 | **高清触感（Voice-Coil 音频触感）** | USB 音频 | 🚧 规划中 | 见第六节方案。就是 Astro 那种“雨滴/玻璃/沙地”的细腻感。它走 USB 音频通道，HID 的震动字节只是低分辨率近似。 |
| 12 | **内置扬声器** | USB 音频 | 🚧 规划中 | 不在 HID 层：DS5 是个 USB 音频设备，占用 4 声道中的前 2 声道（Ch1/Ch2），需往其推送 PCM。 |
| 13 | **麦克风阵列 / 耳机口** | USB 音频 | ❌ 0% | 同样在音频通道，且需要游戏/系统配合，属系统级音频路由管理范畴。 |
| 14 | **蓝牙链路** | HID 协议 | ⚠️ 代码就位 | 78 字节 0x31 格式 + CRC32 已实现，建议 USB 有线连接（USB 是验证过的稳定路径，蓝牙无法获取高质量音频通道）。 |

> **支持度小结**：14 项里 **10 项完整可用**、**1 项待蓝牙真机深入验证**、**3 项位于 USB 音频通道之内**。
> 换句话说：**凡是通过 HID 报告能控制的，本项目均已完全支持**（扳机、双马达、RGB 灯、按键、6轴传感器、电量、触控坐标），差的是音频通道。

## 二、还原度取决于信号源：五类数据源对比

同样的物理执行能力，外部还原度上限彻底取决于**输入数据流的质量与维度**：

| 信号源类型 | 典型延迟 | 能做到什么 | 对应 Profile |
|---|---|---|---|
| **游戏原生触感 API**（Astro / 索尼第一方 PC） | ~0 ms | 材质、剧情、音画同步的毫米级编排 | 外部不可能拦截 |
| **官方物理遥测**（Forza UDP / AC 共享内存 / BeamNG） | 20 ~ 40 ms | 刹车压力→阻力曲线、四轮打滑→左右马达、ABS→14Hz 脉冲、TC、路面粗糙度 | `forza-horizon`<br>`assetto-corsa`<br>`beamng` |
| **手柄自身物理输入** | 4 ~ 8 ms | 瞄准挡墙、扳机断点、开火后坐力、连发节奏、姿态倾斜辅助 | `fps`<br>`generic` |
| **游戏自身震动镜像**（`source/ffb`，规划中） | ~10 ms | 捕获任何游戏“何时/多强在震”，无损换算成自适应扳机与后坐力 | Roadmap `source/ffb` |
| **游戏音频推断**（`source/audio`，规划中） | 30 ~ 60 ms | “有爆炸/枪声”→ 一次脉冲；分频段提取低频包络驱动左右马达 | Roadmap `source/audio` |

## 三、Astro's Playroom 体验的本质还原（机制对比）

从物理执行机制来看，Astro's Playroom 各类代表性手感的外部可还原度：

| Astro 的效果本质 | 外部可做到程度 | 实现依托机制与技术差异 |
|---|---|---|
| **弹簧 / 拉链 / 绳索的阻力形状** | ✅ **很像（高度还原）** | 基于 `slope_feedback` / `feedback` 模式 + 输入行程驱动闭环。 |
| **抓取物体时的持续张力** | ✅ **可做（高度还原）** | 基于 `rigid` 模式 + 输入行程驱动。 |
| **踩在玻璃 / 沙地 / 金属上的震动质感** | ⚠️ **只到“有/无 + 强弱”** | 遥测里有 `surface` 材质枚举，HID 模式只能通过调幅马达模拟粗粒度颠簸；需音频触感（Voice-Coil）才能呈现细腻频谱。 |
| **雨滴敲击、呼吸、小机器人脚步** | ❌ **无法直接做** | 属于预先制作的美术音频触感编排，外部无法从物理量推断出来。 |
| **与剧情 / 动画同步的一击** | ❌ **无法直接做** | 需要游戏内部事件流深度配合。 |

## 四、实际场景能做到什么程度（赛车、射击与第一方对比）

针对具体的游戏品类，分析落地可行性与真实手感预期：

| 游戏场景分类 | 可行性 | 实际效果表现 |
|---|---|---|
| **赛车**：发动机颗粒、换挡冲击、路肩/草地纹理 | ✅ **最有价值** | 遥测里的 `rpm`、`surface`、`slip` 本身就是严谨的物理量，合成出来有理有据，比单纯 8-bit HID 震动明显细腻丰富。 |
| **射击**：枪机后坐的“金属质感” | ✅ **完全可做** | 物理脉冲结合带通噪声，手感远比单一旋转直流马达更像真实“枪械机械撞击”。 |
| **环境细节**：脚步 / 雨滴 / 呼吸等音频触感编排 | ❌ **不可强求** | 这类本质是美术资产；外部只能从游戏混音里提取低频包络猜测，质感会差一个档次。 |
| **叙事体验**：Astro 那种“剧情音画同步的一击” | ❌ **不可行** | 需要游戏专有事件流配合，非通用框架能力所及。 |

## 六、高清触感（Voice-Coil 音频触感）技术方案（Linux & Windows）

### 1. 物理本质：HID 震动与音频触感是对同一对音圈的控制

DualSense 没有传统偏心转子马达，内部是两枚音圈（Voice Coil）。驱动它们有两条通道：

| 通道名称 | 数据带宽 | 开发者能控制什么 |
|---|---|---|
| **HID 报告字节 3/4（本项目已支持）** | 250 Hz 刷新率、8-bit 幅度 | 只有“低频左 / 高频右”两档粗粒度振幅。 |
| **USB 音频通道（PS5 官方使用的通道）** | 48 kHz / 16-bit 任意波形 | 波形、频率、谐波、瞬态包络与细腻纹理全都能精细控制。 |

DualSense 在接入 Linux / Windows 时，本质是一块 **4 声道 / 48 kHz / S16_LE** 的 USB 声卡：
- **Channel 1 & 2**：手柄内置单声道扬声器 / 3.5mm 耳机口；
- **Channel 3 & 4**：**左右音圈触感致动器**（社区逆向与官方一致）。

所谓“高清触感”，就是在软件层往这块声卡的第 3、4 声道写入 PCM 音频流，把音圈当成高保真扬声器驱动。

### 2. 10 分钟跨平台硬件通路验证（Spike）

在编写复杂合成器代码前，先通过简易脚本在真机上验证声道与触感。

#### Linux 环境验证（PipeWire / ALSA）

```bash
# 1. 寻找 DualSense 声卡
cat /proc/asound/cards | grep -i "Wireless\|DualSense"

# 2. 确认声道数（需显示 4 声道 48kHz）
cat /proc/asound/card*/stream0 | grep -A8 -i "dualsense\|wireless"

# 3. 若支持 4 声道，喂入一段 90Hz 的"哒哒"测试声（ch1/2 静音，ch3/4 触感）
python3 - <<'EOF' | pw-cat --playback --channels=4 --rate=48000 --format=s16 -
import math, struct, sys
w = sys.stdout.buffer
for i in range(48000 * 2):  # 持续 2 秒
    on = 1 if (i // 4800) % 2 == 0 else 0          # 0.5 秒开 / 关交替
    v = int(0.5 * on * math.sin(2 * math.pi * 90 * i / 48000) * 32767)
    w.write(struct.pack('<4h', 0, 0, v, v))        # ch1/2=0(静音), ch3/4=触感
EOF

# 注：若系统未安装 pw-cat，可改用 aplay：
# aplay -c4 -r48000 -f S16_LE -t raw -
```

**预期效果**：手柄握把传来极其清脆的“哒哒”物理触感，手柄喇叭完全不发声。
- *异常处理*：如果声音从手柄喇叭漏出，说明声道映射被颠倒，将 `struct.pack('<4h', v, v, 0, 0)` 对调重试即可。

#### Windows 环境验证（WASAPI）

Windows 侧 DualSense 默认可能被枚举为主板双声道设备。验证步骤：
1. 打开 Windows 声音控制面板，将 DualSense 音频属性配置为 **4 声道（Quadraphonic）**；
2. 运行简易 WASAPI 4 声道测试程序，向后置声道推入 90Hz 正弦 PCM。

### 3. 项目架构集成设计（双 Sink 架构）

框架架构无需大动。控制规则运行于控制率（125~250 Hz），音频运行于高采样率（48 kHz），两者通过**触感合成器（Haptic Synth）+ 环形缓冲区（RingBuffer）**衔接：

```
规则引擎 (125~250Hz) ──{intensity, freq, texture}──► 触感合成器 (48kHz) ──PCM──► Audio Sink ──► Ch3/Ch4 音圈
```

- **Linux 输出层**：启动 `pw-cat` / `aplay` 子进程，通过 stdin 管道写入原始 s16le 数据。零 CGO，约 50 行代码，无需调用复杂的 ALSA 底层 ioctl。
- **Windows 输出层**：通过 WASAPI Exclusive 独占模式直接向 4 声道端点写入环形缓冲区。
- **规则扩展语法**：
  ```yaml
  rules:
    - name: abs-vibration
      when: 'abs > 0.1'
      target: haptic_left       # 专有音圈触感 target
      texture: sine             # 纹理：sine | noise | impulse
      frequency: 140            # 振动频率 (Hz)
      value: "0.8"              # 触感振幅
  ```

### 4. 工程工作量与难度评估表

| 工作项 | 预估工时 | 技术难度 | 关键考量 |
|---|---|---|---|
| **设备探测 + PCM 管道输出 + 环形缓冲** | 0.5 ~ 1 天 | 低 | Linux 管道直通，验证端点枚举。 |
| **触感合成原语（正弦/带通噪声/脉冲 + 包络衰减）** | 2 天 | 中 | 提供扎实的物理触感波形生成基础。 |
| **参数插值与防爆音（平滑过渡算法）** | 1 ~ 2 天 | 中 | 避免 250Hz 控制信号跳变导致音频采样发生“咔哒”爆音。 |
| **游戏内容与手感细致调校（发动机、路面、枪机）** | 持续演进 | 高 | 针对各类遥测建立物理触感模型，这是长期工程。 |
| **Windows WASAPI 4 声道端点适配** | 3 ~ 5 天 | 中高 | 处理 Windows 声卡声道隐藏与独占访问模式。 |

### 5. 必须防范的四大工程陷阱

1. **音频设备抢占与休眠**：
   PipeWire 可能会将空闲 ALSA 节点挂起（idle-suspend）；Steam 也可能尝试将整机音频路由至手柄。需要绑定固定 target，并调整 `api.alsa.idle-timeout`，必要时请求独占。
2. **音圈机械安全（DC Offset）**：
   绝对禁止输出直流偏置（DC Offset），长时间大振幅低频极易顶死机械限位。合成器输出端必须串接 **20Hz 高通滤波器（HPF）** 并施加软限幅。
3. **输出延迟控制**：
   系统默认音频缓冲通常在 20~40 ms，会有明显滞后感。必须显式设置 `--latency=10ms`（约 480 采样点），方能获得紧凑的触觉反馈。
4. **与 HID 震动的互斥仲裁**：
   HID 报告中的 Rumble 字节与 USB 音频的 Ch3/4 作用于同一对物理音圈。**一旦激活音频触感，框架必须强制将 HID Rumble 字节置 0**，防止两路同时写入引发机械共振失真。

### 落地建议（Spike 驱动）

**先 Spike，再决策**：
在真机上执行第二小节的 10 分钟 Python 测试脚本。如果佩戴手柄能明显感知到“比现有 8-bit HID 震动细腻且质感更高级”，再正式启动合成器模块的编码；若感知不明显，则优先投入 `source/ffb`（力反馈镜像）开发更具性价比。
